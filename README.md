# Master Router

Мастер-агент: по запросу пользователя определяет нужного ИИ-агента и
проксирует к нему запросы. Доступ к агентам — только через мастер. На текущем
этапе все агенты — локальные сервисы на разных портах с единым контрактом API
(см. [Контракт агента](#контракт-агента)); разнородность транспорта спрятана за
слоем адаптеров, поэтому подключение агента с другим API не меняет мастер.

Мастер **stateless**: не хранит чаты, сообщения и фидбэк — всё это живёт у
агентов и скоупится по `X-User-Id`. Задача мастера — роутинг, выбор адаптера и
проксирование.

## Архитектура
 
```
                 ┌─────────────────────────────────────┐
   клиент  ─────▶│            Master Router            │
                 │                                     │
                 │  routing/   embedding → llm         │
                 │  adapters/  create_session / stream │
                 └───────┬───────────────┬─────────────┘
                         │               │
              ┌──────────▼───┐   ┌───────▼──────┐   ...
              │  агент ЕПоЗ  │   │  агент OCR   │
              │  :8443       │   │  :xxxx       │
              └──────────────┘   └──────────────┘
```
 
Мастер — единственная точка входа. Агенты сидят на localhost и доверяют
заголовку `X-User-Id`, который проставляет мастер (на текущем этапе — берётся
из заголовка клиента.

## Роутинг

`MasterRouter.route()` определяет агента каскадом из двух слоёв. Каждый
следующий слой запускается, только если предыдущий не дал ответа:
 
1. **embedding_router** — семантическая близость запроса к описаниям агентов
   через `intfloat/multilingual-e5-small` (косинусная мера, порог отсечения).
2. **llm_router** — классификация запроса моделью `gemma2:2b` через Ollama,
   ответ форсится в JSON.
Если ни один слой не дал валидного агента, запрос уходит на `FALLBACK_AGENT`
(`chat`). Блокирующие вызовы (`encode`, `client.chat`) вынесены в
`asyncio.to_thread`, чтобы не блокировать event loop.
 
В авто-роутинге участвуют только агенты с `routable=True`. Инструменты без
диалога (OCR) помечены `routable=False` — их нельзя выбрать по тексту, к ним
обращаются напрямую по id через их capability-маршрут.

## Слой адаптеров

Мастер общается с агентом через `AgentAdapter` в терминах намерений
(`create_session`, `stream_chat`, …), а не HTTP-путей. Транспорт выбирается по
полю `transport` в реестре:
 
| transport  | адаптер              | для кого                                        |
|------------|----------------------|-------------------------------------------------|
| `contract` | `ContractHTTPAdapter`| диалоговые агенты на каноническом контракте (ЕПоЗ)|
| `external` | `ExternalAPIAdapter` | чужой API вендора (скелет; беседы хранит сам)   |
| `ocr`      | `OCRAdapter`         | инструмент файл-в/текст-из, без сессий          |
| `cognitum` | `CognitumAdapter`    | агенты на оркестраторе (план)                   |
 
Не-стримовые операции возвращают `AgentResponse(status, content, media_type)` —
конверт несёт статус-код, поэтому `204`/`404` проходят насквозь через любой
транспорт. Добавление агента, укладывающегося в контракт, — запись в
`registry.py`; число маршрутов мастера от числа агентов не зависит.

## Ядро контракта и возможности
 
Контракт делится на **ядро** (обязательное для всех адаптеров) и **возможности**
(capabilities — необязательные умения, есть не у каждого).
 
Ядро (`@abstractmethod` в `base.py`) реализует любой адаптер: `create_session`,
`list_sessions`, `get_messages`, `rename_session`, `delete_session`,
`stream_chat`, `set/get/delete_feedback`. Агент, у которого чего-то из ядра нет
(OCR не имеет сессий), реализует эти методы честными заглушками — `404`, а не
падение; а `stream_chat` у недиалогового агента отдаёт `CapabilityNotSupported`.
 
Возможности — необязательные методы с дефолтом «не умею»
(`raise CapabilityNotSupported`). Каждая возможность:
 
- объявляется адаптером как метод (`run_ocr`, `upload_document`, …);
- перечисляется в `capabilities` агента в реестре;
- имеет **один общий** маршрут мастера (рост маршрутов O(возможностей), а не
  O(агентов)).
Перед вызовом маршрут проверяет `require_capability(agent_id, "...")`; если
возможность не объявлена — `404`. На случай рассинхрона (объявлена в реестре, но
не реализована в адаптере) в `main.py` висит обработчик `CapabilityNotSupported`
→ `404`. `GET /agents` отдаёт `capabilities`, поэтому фронт сам решает, что
показывать для выбранного агента (поле ввода, кнопку загрузки файла и т.п.).

## Эндпоинты мастера

Все проксирующие эндпоинты требуют заголовок `X-User-Id: <uuid>` и
пробрасывают его агенту без изменений. Статус-коды и тела ответов агента
проходят насквозь (включая `204 No Content` и `404` на чужой ресурс).
`session_id` и `message_id` для мастера опаковы — он не интерпретирует их.

### Служебные

| Метод  | Путь      | Назначение                              |
|--------|-----------|-----------------------------------------|
| `GET`  | `/agents` | Список включённых агентов (`id`, `name`)|
| `POST` | `/route`  | Определить агента по тексту запроса      |

`POST /route` — тело `{"message": "..."}`, ответ `{"agent": "epoz"}`.

### Сессии (прокси на агента)

| Метод    | Путь                                              |
|----------|---------------------------------------------------|
| `POST`   | `/agents/{agent_id}/sessions`                     |
| `GET`    | `/agents/{agent_id}/sessions`                     |
| `GET`    | `/agents/{agent_id}/sessions/{session_id}/messages`|
| `PATCH`  | `/agents/{agent_id}/sessions/{session_id}`        |
| `DELETE` | `/agents/{agent_id}/sessions/{session_id}`        |

### Чат (SSE-стрим)

| Метод  | Путь                                            |
|--------|-------------------------------------------------|
| `POST` | `/agents/{agent_id}/sessions/{session_id}/chat` |

Тело `{"message": "..."}`, ответ — поток `text/event-stream` (формат событий
см. [Контракт агента](#контракт-агента)).

### Фидбэк (прокси на агента)

| Метод    | Путь                                            |
|----------|-------------------------------------------------|
| `POST`   | `/agents/{agent_id}/messages/{message_id}/feedback` |
| `GET`    | `/agents/{agent_id}/messages/{message_id}/feedback` |
| `DELETE` | `/agents/{agent_id}/messages/{message_id}/feedback` |

### Авто-роутинг

| Метод  | Путь    | Назначение                                  |
|--------|---------|---------------------------------------------|
| `POST` | `/chat` | route → создать сессию → стримить, за раз    |

### Возможности (capabilities)
 
Общий маршрут на каждое умение; доступен только агентам, у которых умение
объявлено в `capabilities` (иначе `404`). Тело — `multipart/form-data`, поле
файла — `file`.
 
| Метод  | Путь                          | Возможность | Ответ                       |
|--------|-------------------------------|-------------|-----------------------------|
| `POST` | `/agents/{agent_id}/ocr`      | `ocr`       | SSE (`token` + `[DONE]`)    |
| `POST` | `/agents/{agent_id}/documents`| `documents` | статус загрузки             |
 
### Авто-роутинг
 
| Метод  | Путь    | Назначение                                  |
|--------|---------|---------------------------------------------|
| `POST` | `/chat` | route → создать сессию → стримить, за раз    |

Тело:

```json
{
  "message": "...",
  "agent_id": "epoz",   // опционально: если задан — роутинг пропускается
  "session_id": 1       // опционально: если null — создаётся новая сессия
}
```

Маршрутизатор срабатывает только на границах разговора — три входа:

| Что прислал клиент                 | Поведение                                   |
|------------------------------------|---------------------------------------------|
| `{message}`                        | роутинг → новая сессия (новый разговор/возврат) |
| `{message, agent_id}`              | роутинг пропущен → новая сессия (ручной выбор)  |
| `{message, agent_id, session_id}`  | роутинг пропущен → стрим в существующую сессию  |

`session_id` принадлежит конкретному агенту, поэтому валиден только вместе с
`agent_id`: запрос с `session_id`, но без `agent_id` → `422`. Смена агента всегда
означает новую сессию.

В заголовках ответа возвращаются `X-Agent-Id` и `X-Session-Id`. Клиент
передаёт их обратно в следующем запросе (`agent_id`, `session_id` в теле),
чтобы продолжить разговор в той же сессии того же агента (**sticky-сессии**).

## Контракт агента

Мастер форвардит по контракту, а не по конкретному агенту, — поэтому каждый
contract-агент обязан реализовывать одинаковую форму API. Добавление нового
агента, соблюдающего контракт, требует только записи в `registry.py`. Агенты с
другим API подключаются своим адаптером, но наружу выдают тот же канонический
SSE.

Обязательная часть контракта:

- скоупинг всех ресурсов по `X-User-Id`; обращение к чужому ресурсу → `404`;
- `POST /sessions` возвращает объект с полем `id` (на него завязан `/chat`);
- `POST /sessions/{id}/chat` отдаёт SSE в формате:

  ```
  data: {"chunks": [{"text": "...", "source": "doc1.pdf", "score": 0.87}]}
  data: {"token": "RAG"}
  data: {"token": " — это"}
  data: {"message_id": 2}
  data: [DONE]
  ```

  - `chunks` — первое событие, извлечённые фрагменты-контекст (только при
    RAG-запросе; при small-talk отсутствует);
  - `token` — токены ответа, включая блок источников в конце;
  - `message_id` — ID сохранённого сообщения (для фидбэка);
  - `[DONE]` — завершение потока.

Полная спецификация ручек агента (`/sessions`, `/messages`, `/feedback`) —
едина для всех агентов и описана в документации агента.

## Реестр агентов

`registry.py` — единственное место, где задаются агенты:

```python
@dataclass
class AgentInfo:
    id: str
    name: str
    url: str
    description: str
    enabled: bool = True
    transport: str = "contract"          # "contract" | "external" | "cognitum"
    config: dict = field(default_factory=dict)


AGENTS: dict[str, AgentInfo] = {
    "epoz": AgentInfo(
        id="epoz",
        name="ЕПоЗ",
        url="http://127.0.0.1:8001",
        description="Закупки, ЕПоЗ",
    ),
    # ...
}
```

- `description` используется embedding- и llm-роутерами для классификации —
  чем содержательнее (с примерами запросов), тем точнее роутинг.
- `enabled=False` исключает агента из `/agents` и из роутинга.
- `transport` выбирает адаптер; у `contract` пустой `url` → `503`.
- `capabilities` — умения агента; проверяются на capability-маршрутах и
  отдаются в `GET /agents`.
- `routable=False` убирает агента из кандидатов авто-роутинга.
- `config` — пер-агентные переопределения дефолтов из `config.py`.

> На текущем этапе реально запущены **ЕПоЗ** и **OCR**. Остальным агентам имеет
> смысл выставить `enabled=False`, пока их сервисы не подняты, — иначе роутер
> может выбрать агента без рабочего `url`.

## Обработка ошибок
 
Проксирование стрима устроено так, чтобы различать сбои до и во время потока:
 
- агент **недоступен** или ответил `4xx/5xx` **до начала** стрима → клиент
  получает чистый `502` с понятным телом (статус ещё можно задать, поток не
  начат). Для этого первый чанк вычитывается до создания `StreamingResponse`;
- соединение оборвалось **в середине** стрима → статус уже отдан (`200`),
  поэтому в поток дописывается SSE-событие `data: {"error": "..."}`. Фронту
  достаточно проверять каждое событие на наличие поля `error`;
- обращение к возможности, которой у агента нет → `CapabilityNotSupported`,
  которое обработчик в `main.py` превращает в `404`.


## Запуск

```bash
pip install -r requirements.txt

ollama pull gemma2:2b

touch .env
```
Пример заполнения `.env`
```
# --- сеть мастера ---
HOST=127.0.0.1
PORT=8000
TIMEOUT_KEEP_ALIVE=300

# --- исходящие к contract-агентам ---
AGENT_TIMEOUT=300
AGENT_VERIFY_TLS=false
AGENT_MAX_CONNECTIONS=200
AGENT_MAX_KEEPALIVE=40

# --- роутинг ---
FALLBACK_AGENT=chat

# --- models ---
OLLAMA_MODEL=gemma2:2b
EMBEDD_MODEL=intfloat/multilingual-e5-small
```
или
```
# --- сеть мастера ---
HOST=127.0.0.1
PORT=8000
TIMEOUT_KEEP_ALIVE=300

# --- исходящие к contract-агентам ---
AGENT_TIMEOUT=300
AGENT_VERIFY_TLS=false
AGENT_MAX_CONNECTIONS=200
AGENT_MAX_KEEPALIVE=40

# --- роутинг ---
FALLBACK_AGENT=chat

# --- models ---
OLLAMA_MODEL=qwen3.6:35b
EMBEDD_MODEL=BAAI/bge-m3
```
```bash
# запуск
python main.py
# или
uvicorn main:app --host 127.0.0.1 --port 8000 --reload
```

Мастер поднимается на `http://127.0.0.1:8000`. `timeout_keep_alive=300`
и `timeout=300` у httpx-клиента — под долгие SSE-стримы.

## Примеры запросов

```bash
# определить агента
curl -X POST http://127.0.0.1:8000/route \
  -H "Content-Type: application/json" \
  -d '{"message": "как подать заявку на тендер по 223-фз"}'
# {"agent": "epoz"}

# авто-роутинг + стрим (новая сессия)
curl -N -X POST http://127.0.0.1:8000/chat \
  -H "Content-Type: application/json" \
  -H "X-User-Id: 11111111-1111-1111-1111-111111111111" \
  -d '{"message": "что такое ЕПоЗ"}'

# продолжить ту же сессию (agent_id и session_id из заголовков прошлого ответа)
curl -N -X POST http://127.0.0.1:8000/chat \
  -H "Content-Type: application/json" \
  -H "X-User-Id: 11111111-1111-1111-1111-111111111111" \
  -d '{"message": "а какие сроки", "agent_id": "epoz", "session_id": 1}'

# OCR: файл-в/текст-из, напрямую по id (без сессии), поле файла — file
curl -N -X POST http://127.0.0.1:8000/agents/ocr/ocr \
  -H "X-User-Id: $U" \
  -F "file=@scan.png"
# data: {"token": "распознанный текст"}
# data: [DONE]
```
